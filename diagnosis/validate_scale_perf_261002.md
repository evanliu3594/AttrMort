# 规模与性能验证：真实数据下的 AttrMort（261002）

> 本文只记录**本次实测**与由其**外推**的结论；每条数字都标注来源与证据等级。
> 分工：T4（scale-perf）。Lead 的 `scale-probe.R` 数字标注为「Lead 实测」，其余为「T4 实测」。
> 证据等级沿用 `result-verification`：V1 = 现场复现（含手算基准/独立实现比对），V2 = 产物核对，V3 = 静态通读，V4/V5 = 推理。
>
> 测量时的代码版本：HEAD = `9e85713`（工作区含 T1/T2 未提交改动，见 §2.4 版本钉扎）。
> 机器：Windows 10 x64，R 4.6.1，terra 1.9.50，dplyr 1.2.1，16 逻辑核，物理内存 15.79 GB。

## 0. 结论摘要

1. **0.1° 全球（真实 netCDF 4.68e6 格，其中有效 1.74e6 格 + LandScan 9.33e8 格）在 16 GB 机器上能跑完，但「读」和「白搬」吃掉了绝大部分成本**：`mortality()` 全球单域 + `chunk_ages = 1` 实测 **482.5 s**、R 堆峰值 **8.27 GB**（§4.3）；其中为服务一个 **6699 格**的 Lao 窗口，旧 `.aggregate_pop()` 实读整幅 **9.33e8 格** LandScan、耗时 **16.14 s**，而这条窗口路径上的完整 `mortality()` 其余全部阶段合计只有 **0.82 s**（§4.2）。
2. **现有内核的真正上界不是「格数 × 分层数」的乘积本身，而是 PWRR 扇出的重复次数**：`.pwrr_by_domain()` 每一遍都要建 **格数 × 全部 endpoint_age = 1,737,383 × 15 = 26,060,703 行**的表（实测 1.39 GB / 9.66 s），且**与有多少格带域标签无关**（只给 2,156 格标签时行数完全相同，`drop_na()` 后才剩 32,340 行）。年龄分块切的是 `mort_rate`/`age_struc`，没切 `RR_tbl`，所以分块既不省内存、又把 PWRR 成本乘以遍数（实测：同规模 `chunk_ages = 1` 比一遍**慢 8.0 倍**、峰值还略高，§5.4）。
3. **内存模型低估 3.1–4.3 倍**：`.chunk_peak_bytes()` 按 64 B/（格 × 层）估，实测约 2.8–4.0 KB/格（15 层）（§5.4）。按实测标定，0.1° 全球 + GEMM 一遍约 4.9 GB，已贴本机上限；5COD/MRBRT（75–90 层）在现架构下不可行。
4. **区域分析把全世界算了一遍**：全球暴露栅格 + 只圈 Lao 时，进入计算的是 **1,737,383 格**（掩膜后有效格），实际有域标签的只有 **2,156 格**（**806×**；按模板格数算 **2171×**），域级长表被撑到 1,778,347 行，而结果只需要 32,340 行（§6）。
5. **两处规模缺陷已修复**（Lead 批准，commit `0113201`，§9）：`.aggregate_pop()` 的守恒校验改为「同支撑集」比较（旧实现任何区域运行必虚报，Lao 窗口实测虚报 **98.8630%**，而真值为 **0.000000%**），并前置裁剪到模板足印（Lao 窗口 **16.14 s → 0.16 s**，聚合结果与不裁剪路径逐格相同）；顺带修掉 `align_to_target()` 把 CRS84 与 EPSG:4326 当两个 CRS 的字符串比较（F3）。
6. **尚未修复、需拍板的规模问题**：0.01°（1 km）成对栅格在非交互会话**静默回退**到 0.1°（§7.1）；模板不在 pop 聚合块网格上时，人口场被 `resample(method="sum")` 在块内抹平，实测逐格中位误差 **16.6%**、最大 **119%**、窗口总量 **+3.94%**（§7.3，V1 手算基准）。

## 1. 方法与复现

### 1.1 计时与内存的测量方法（不新增依赖）

| 指标 | 方法 | 说明 |
|---|---|---|
| wall time | `Sys.time()` 前后差 | 每阶段单独计时 |
| R 堆峰值 | `gc(reset = TRUE)` → 阶段后 `sum(gc(full = TRUE)[, 6])` | `gc()` 第 6 列是 max used 的 MB；第 5 列是**单元数**，不是字节（第一版脚本踩过这个坑） |
| 进程峰值 | `ps::ps_memory_info(ps::ps_handle())` 的 `wset` / `peak_wset` | `ps` 只出现在**包外 harness**，不是包依赖；`wset` 前后差给阶段增量，`peak_wset` 给进程生命周期峰值 |

## 3. 数据规模事实（T4 实测，`m0-facts.R`）

| 项 | LandScan 2023 GeoTIFF | PM2.5 0.1° netCDF |
|---|---|---|
| 尺寸 | 21600 × 43200 = **933,120,000** 格 | 1300 × 3600 = **4,680,000** 格 |
| `res()`（17 位） | `0.0083333333329999992` | `0.099999998304107912` / `0.099999998238015128` |
| extent x | -180 … 179.9999999856 | **-179.9999969474** … 179.9999969474 |
| extent y | -89.9999999928 … 89.9999999999 | -60.0000007621 … 69.9999969474 |
| datatype / NAflag | INT4S / NaN | 空 / NaN |
| 文件大小 | 85.64 MB | 5.02 MB |

关键事实：

- **netCDF 的 `res` 不是精确 0.1**（`0.0999999983041`），extent 也不是精确 ±180（差 3.05e-6°）。模板由曝光 extent + `resolution = 0.1` 生成，因此模板网格与 LandScan 的 0.1° 聚合块网格之间存在 **3.05e-6°（≈3e-5 个格）的偏移**，不是 0 也不是半格。
- **暴露栅格有 2,942,617 格是未声明的 -999 填值**（T4 实测：`== -999` 与 `<= 0` 计数相同），占 4.68e6 格的 **62.9%**；`> 0` 的只有 **1,737,383** 格。这直接决定规模：全球 0.1° 的有效分析格是 1.74e6，不是 4.68e6。
  （-999 的契约问题由 T1 负责，`diagnosis/validate_raster_ingest_261002.md`；本文只把它当作规模事实。）
- LandScan 在海洋上是 NA：`.aggregate_pop()` 到全球模板后 **3,189,515 格为 NA**，有值 **1,490,485** 格（T4 实测，§4.4）。所以「暴露有效」∩「人口有值」≈ 1.49e6 格。
- `rr_std("GEMM","MEAN")` 返回 **45,015 行 = 3,001 个浓度键 × 15 个 endpoint_age 层**（T4 实测）。真正参与 join 的扇出是「每格 × 15」，45,015 行只是哈希表侧的大小（Lead 的 `468万 × 4.5万` 是原始注释，实测的行积是 格数 × 15，见 §5.1）。

## 4. 分阶段计时与内存

### 4.1 测量口径

每阶段：`gc(reset=TRUE)` → `wset` 采样 → 计时 → `gc(full=TRUE)` → `wset` 采样。`heap_mb` 是 R 堆 max used，`wset` 是进程工作集（含 terra 的 C++ 内存）。

### 4.2 Lao 切片（真实 GBD 表 + 真实边界，`m2-lao-stages.R`，T4 实测）

模板 = 曝光窗口 0.1°（87 × 77 = **6,699 格**，x 100.0–107.7，y 13.9–22.6）。

| 阶段 | wall (s) | R 堆 max (MB) | wset 前→后 (MB) | 对象 (MB) |
|---|---|---|---|---|
| `rast(netCDF)` + `crop` 到 Lao 窗口 | 0.04 | 124.1 | 234.5 → 243.4 | 0.0 |
| 掩膜 `conc <= 0 → NA` | 0.01 | 124.4 | 237.5 → 237.7 | 0.0 |
| `rast(LandScan)`（933M 格） | 0.04 | 140.2 | 237.8 → 238.7 | 0.0 |
| **`.aggregate_pop(整幅 → 0.1° 窗口)`** | **16.14** | 155.6 | 238.7 → 288.5 | 0.0 |
| `raster_to_grid(conc)` | 0.02 | 132.4 | 288.5 → 289.2 | 0.2 |
| `raster_to_grid(pop)` | 0.07 | 159.0 | 289.3 → 245.3 | 0.2 |
| `ne_countries(110) → LAO` | 0.02 | 133.6 | 245.3 → 247.2 | 0.0 |
| `shapefile_to_grid(LAO → 模板)` | 0.07 | 155.2 | 247.2 → 251.7 | 0.1 |
| 读 GBD 2023 → `mort_rate` | 0.55 | 222.4 | 251.7 → 298.6 | 0.0 |
| 读 GBD 2021 → `age_struc` | 0.05 | 169.1 | 298.6 → 304.2 | 0.0 |
| `rr_std("GEMM","MEAN")` | 0.28 | 270.9 | 304.2 → 341.2 | 1.5 |
| join 链到 `drop_na()`（1 个年龄层） | 0.13 | 224.4 | 328.8 → 357.9 | 0.5 |
| `.widen_mort()`（1 个年龄层） | 0.01 | 187.3 | 357.4 → 357.5 | 0.5 |
| 内核 `chunk_ages = 1`（15 遍） | 2.70 | 349.3 | 357.6 → 361.7 | 0.9 |
| 内核 `chunk_ages = NULL`（自动 = 15，一遍） | **0.42** | 333.0 | 361.3 → 363.5 | 0.9 |
| `mortality()` 端到端（pop 传已聚合栅格） | 0.82 | 362.7 | 362.7 → 378.9 | 0.0 |
| 进程峰值 wset | — | — | **1,942 MB** | — |

**读数**：

- 「算」很便宜、「读」很贵：Lao 窗口 6,699 格的完整 `mortality()` 是 **0.82 s**，而只为把 LandScan 聚到这 6,699 格就花了 **16.14 s**（把 9.33e8 格整幅读一遍）——**19.7 倍**。
- 内核分块在小规模上是**纯开销**：`chunk_ages = 1` 用 **2.70 s**（15 遍，每遍 0.18 s，主要是每遍重建 join 的固定成本），不分块 **0.42 s**，**6.4 倍**。分块的价值只在大格数上体现（§5）。
- 两种分块结果逐列一致：`all.equal(chunk_ages = 1, chunk_ages = NULL)` = TRUE（tolerance 1e-12）。
- 结果：`mortality()` 端到端 **6,699 格 → 2,155 格有标签 → 6,248 行进内核**（451 格是海面、pop 为 NA），LAO 总归因死亡 3018.507（数值正确性由 T3 负责，此处只作规模证据）。

### 4.3 全球 0.1°（`m3-global.R`，T4 实测）

模板 = 曝光栅格自身的 0.1° 网格（1300 × 3600 = 4,680,000 格，-60..70）；曝光掩掉未声明填值后 **1,737,383** 格有效；人口为整幅 LandScan 聚合到该网格。

| 阶段 | wall (s) | R 堆 max (MB) | wset 前→后 (MB) | 对象 (MB) |
|---|---|---|---|---|
| `rast(netCDF)` + 掩膜 `<= 0 → NA` | 0.46 | — | 234 → 310 | — |
| `rast(LandScan)`（933M 格） | 0.04 | — | 309 → 310 | 0.0 |
| **`.aggregate_pop(整幅 → 全球模板)`** | **22.15**（修复前）／**36.4**（修复后，含守恒校验多读一遍源） | 177.6 | 310 → 364 | 0.0 |
| `raster_to_grid(conc, 全球)` | 1.41 | 536.0 | 394 → 448 | 40.0 |
| `raster_to_grid(pop, 全球)` | 1.02 | 626.0 | 475 → 509 | 34.4 |
| `shapefile_to_grid(Lao 边界 → 全球模板)` | 1.73 | 575.7 | 407 → 394 | 0.1 |
| `.attach_admin`（Lao 标签贴到全球 calc_fild） | 1.77 | 767.7 | 536 → 551 | 33.4 |
| join 链（全球 calc_fild + 15 年龄层） | 1.73 | 738.7 | 549 → 649 | 122.5 |
| `.pwrr_by_domain()` 的 join（1.737e6 格 × 15 层） | **9.66** | — | 750 → 2086 | 1392.1 |
| 同一 join，只给 2,156 格标签 | 3.15 | — | 2388 → 3722 | — |
| **`mortality()` 全球 + 单域（矩形标签）+ `chunk_ages = 1`（15 遍）** | **482.47** | **8269.9** | 527 → 515 | 205.0 |

读数：

- **全球 0.1° 能跑完**（未 OOM），但 `chunk_ages = 1` 要 **8 分钟**，且进程 R 堆峰值 **8.27 GB**（实测；机器 15.79 GB，测量期间空闲内存一度只剩 2.6 GB）。默认 `chunk_ages = NULL`（= 5 层/遍 → 3 遍）按 m5 的每次 join 成本外推会更快（见 §5.4）。
- 单看 `.pwrr_by_domain()`：**每次都建 26,060,703 行（= 1,737,383 格 × 15 层）的表，1.39 GB，9.66 s**，而这与「有多少格带域标签」无关（只给 2,156 格标签时行数**完全相同**，只有 `drop_na()` 之后剩 32,340 行）。`chunk_ages = 1` 的 15 遍会把这 9.66 s 的表**建 15 次**。
- 这是本次最重要的规模发现：**年龄分块切的是 `mort_rate`/`age_struc`，没切 `RR_tbl`**，所以 PWRR 扇出（cells × 全部 endpoint_age）与 pass 数无关，分块只降低第二段 join 的行数、却把 PWRR 成本乘以 pass 数。Lao 切片上这看不出来（分块反而慢 6.4 倍，§4.2），全球尺度上它是 482 s 的主因。

### 4.4 全球运行的规模账（`m3-global.R` + `m5-waste.R`，T4 实测）

```
calc_fild rows: 1,737,383 | labelled cells: 2,156
+ conc   : 1,737,383
+ pop    : 1,737,383 | pop NA: 251,504
+ mort   : 1,778,347 rows (fan-out at this join)
+ age    : 1,778,347 rows
Lao-only 标签下的 PWRR join: 26,060,703 行 → drop_na 后 32,340 行
```

即：为得到 **2,156 格 × 15 层 = 32,340 行**的结果，管线先在 1,737,383 行上做全部 join，再在 **26,060,703 行**上做 PWRR 加权——**806×** 与 **806×** 的无效搬运（对模板格数则为 **2171×**）。

## 5. 上界：(格子数 × 年龄层 × 端点)

### 5.1 实测「每行字节」——一切外推的锚

| 数据 | 列数 | 每行字节 | 来源 |
|---|---|---|---|
| Lao 切片长表（x,y,location,conc,pop,endpoint,age,mortrate,RR,PWRR） | 10 | **92.3 B** | T4 实测（`m2-lao-stages.R`） |
| 全球长表（Lao-only 标签，同 join 链） | 9 | **72.2 B** | T4 实测（`m3-global.R`） |
| 宽表（6,248 行 × 10 列，1 个年龄层） | 10 | 0.5 MB 对象 | T4 实测 |

长表行数 = **格数 × 该格匹配到的分层数**（`endpoint × age`）。扇出发生在 `mort_rate` join（键只有 `location`）：Lao 切片实测 6,699 行 → **100,485 行**（×15），全球实测 1,737,383 行 → **1,778,347 行**（只有 2,156 格匹配到域，其余 1 格/行）。

**结论 5.1**：以 92.3 B/行为准，**单份长表 GB ≈ 格数 × 分层数 × 92.3 / 1024³ = 格数 × 分层数 × 8.6e-8**。dplyr 的 join / `drop_na()` 至少同时持有新旧两份，故 **峰值 ≈ 1.72e-7 × 格数 × 分层数 GB**。

### 5.2 OOM 判据（8 GB 预算）

把 §5.1 的峰值公式反过来，得到可直接用的判据：

```
安全条件（8 GB 预算，2 份）:   格数 × 分层数 ≤ 4.7e7
包自带模型的安全条件:          格数 × 分层数 ≤ 1.34e8  （.chunk_peak_bytes 视 8 份 8 字节向量）
```

| 规模 | 格数 × 分层 | 单份长表 | 峰值（含 2 份） | 判定（8 GB 预算） |
|---|---|---|---|---|
| Lao 切片 | 1.0e5 | 8.6 MB | 17 MB | 安全 |
| 全球 0.1°（有效 1.74e6 格 × 15） | 2.6e7 | 2.2 GB | 4.5 GB | 安全（实测见 §4.4） |
| 全球 0.1°（模板 4.68e6 格 × 15） | 7.0e7 | 6.0 GB | 12.1 GB | **不分块 OOM**；分块（5 层/遍）后 4.0 GB/遍 |
| 全球 0.1° + 5COD（75 层） | 3.5e8 | 30 GB | 60 GB | 必须 1 层/遍（2.2 GB/遍） |
| 全球 0.1° + MRBRT2021（90 层） | 4.2e8 | 36 GB | 72 GB | 必须 1 层/遍（2.2 GB/遍，实测模型预测 2.3 GB） |
| 题面「4.68e6 格 × 51 个 endpoint_age 列」 | 2.4e8 | 20.5 GB | 41 GB | 同上，**必须分块** |
| 0.05° 全球（1.296e7 格 × 15） | 1.9e8 | 16.7 GB | 33 GB | 分块 2 层/遍 → 4.8 GB/遍（外推，贴预算上限） |
| 1 km 全球陆地（约 2.7e8 格 × 15） | 4.1e9 | 350 GB | 700 GB | **不可能** |

（除 Lao 与全球 0.1° 两行为实测，其余为按 §5.1 公式的外推。）

### 5.3 包自带的年龄分块（实测调用）

`.resolve_chunk_ages(NULL, n_cells, n_ages, n_endpoints)`（预算 2 GiB）：

| 调用 | 返回（每遍层数） | 遍数 | 包模型单遍峰值 |
|---|---|---|---|
| `(NULL, 6.48e6, 15, 1)`（0.1° 全球陆地 + GEMM） | 5 | 3 | 1.93 GB |
| `(NULL, 4.68e6, 15, 1)` | 5 | 3 | 1.52 GB |
| `(NULL, 2.592e7, 15, 1)`（0.05°） | 2 | 8 | 1.55 GB |
| `(NULL, 6.48e6, 75, 5)`（5COD） | 1 | 15 | 1.93 GB |
| `(NULL, 9.33e8, 15, 1)`（1 km） | 1 | 15 | **55.6 GB** ← 模型自己承认不可能 |

最后一行是**现架构的硬边界**：即使一层一遍，1 km 全球的一遍长表也远超内存，这正对应 `R/AGENTS.md` 第七节第 1 条要新增分块流式引擎的理由。

### 5.4 模型标定与「分块到底省不省内存」（`m4-chunk.R`，T4 实测）

每进程一个用例，读 `peak_wset` 的增量（基线 ~280 MB），合成网格键唯一、GEMM 15 层、单域：

| n_cells | `chunk_ages` | 一遍行数 | wall (s) | 峰值增量 (MB) | 模型预测 (MB) | 实测/模型 |
|---|---|---|---|---|---|---|
| 100,000 | 15（一遍） | 1,500,000 | **3.76** | 397 | 92 | **4.34×** |
| 100,000 | 1（15 遍） | 100,000 | **30.24** | 464 | 6 | **75.9×** |
| 400,000 | 15（一遍） | 6,000,000 | 10.82 | 1,123 | 366 | **3.07×** |

**结论**：

1. `.chunk_peak_bytes()` 在正常路径上**低估 3.1–4.3 倍**：它按 `8 bytes × 8 copies = 64 B` 每（格 × 层）估，实测约 **2.8–4.0 KB/格**（15 层）。原因不是「每行字节」——实测长表 53–92 B/行——而是**它没有计入 PWRR join 用的是全部 15 层、与 pass 无关**（见 §4.3），也没有计入 dplyr 同时持有新旧两份以及 15 个宽表分块。
2. **`chunk_ages` 在本机实测中不省内存、只花时间**：同一个 100k 格问题，`chunk_ages = 15`（一遍）峰值 397 MB、3.76 s；`chunk_ages = 1`（15 遍）峰值 **464 MB（更高）**、30.24 s（**8.0×**）。因为 PWRR 那一步（格 × 全部 15 层）在每一遍里都要重建一次，分块只压缩了第二段 join。
3. 这条直接影响 `R/AGENTS.md` §7.1 的引擎计划：计划里的「第一遍按 (域, 年龄, 端点) 累积 Σpop 与 Σpop·RR」正是把 PWRR 变成**一遍**的事，方向是对的；但**护栏里沿用的内存预算常数必须先按本表重标定**，否则 2 GiB 的预算会被当成 5–6 GiB 用。
4. 换算到本机（15.79 GB，实测空闲 7.3 GB）：0.1° 全球 + GEMM（1.74e6 有效格）一遍要 ~4.9 GB（按 2.8 KB/格外推），**已经贴着上限**；5COD/MRBRT（75–90 层）必须一层一遍，而一层一遍恰恰又受 §4.3 的 PWRR 常数成本支配——现架构在这一点上无解，必须改内核。

### 7.2 整倍数判定（`.aggregate_pop()` 的 `fact` 测试）

真实对：`fact = res_t / res_r = 11.999999796972951`（x）、`11.999999789041816`（y）。
`|fact - round(fact)| = 2.03027e-07` / `2.10958e-07`，判据是 `< 1e-6` → **通过，但余量只有 4.9×／4.7×**。

用真实 LandScan 的一小窗（120×120 格）做对照（`m1b-conservation.R`）：

| 源声明的 `res` | `fact` | `|fact-round|` | 走哪条分支 | 实测结果 |
|---|---|---|---|---|
| `1/120`（terra 报告值） | 12.000000000 | 1.8e-15 | aggregate | 与手算面积加权完全一致 |
| `0.008333`（产品把 1/120 写成 5 位） | 12.000480019 | 4.8e-4 | **plain resample**（告警） | 总量与手算一致（0.000005%） |

### 7.3 守恒：手算基准的结论（V1）

基准：自写 `exact_on()`（按目标几何逐格做**面积加权重叠**求和）+ 12×12 块和 + 单个目标格的**双重循环暴力求和**（`m1h-bruteforce.R`）。取向先钉扎（`m1d-orientation.R`：`as.matrix(wide=TRUE)` 第 1 行 = 最北行，实测确认），避免「基准自己反了」的假阳性——第一版基准确实反了，已改正后重跑。

| 用例 | 与手算基准的差 |
|---|---|
| 合成渐变场 0.05°→0.1°，偏移 0／0.05／0.025／0.0125° | 逐格 0.0000%、总量 0.000000% |
| 真实 LandScan 1°×1° 窗 → 0.1° 模板，偏移 0.10°（在格网上） | 逐格 0.0000%、总量 2e-5 相对 |
| 真实 LandScan，偏移 0.05°（半个聚合块） | **逐格中位 16.6%、最大 119%；窗口总量 +3.94%** |
| 真实 LandScan，偏移 0.025° | 逐格中位 9.5%、最大 89%；总量 +1.25% |
| 均匀场非整倍数（0.02°→0.05°） | 总量 0.000000% |
| 渐变场非整倍数×2.5（0.02°→0.05°，plain 分支） | 逐格最大 7.98%、**逐格中位 0.0000%**，总量 0.000000% |

**机制**（`m1e-decompose.R` 实测拆解，非推理）：

- `terra::aggregate(w, fact = 12)` 与手算 12×12 块和**逐格一致**（max |diff| = 0）→ 聚合步正确。
- `.aggregate_pop()` 的输出 == `aggregate + resample(method="sum")`（逐格 identical = TRUE）。
- `resample(sum)` 对**聚合后的块**做面积加权混合，与手算一致（0.0000%）→ 重采样步本身也是「按面积」的。
- 那 +3.94% 从哪来？**两个基准在不同的层级上做面积加权**：手算基准在**原始 30 arc-sec 格**上按重叠面积求和（真值），而管线先把 30 arc-sec 聚成 0.1° 块、再把这些**块**按重叠面积摊到目标格——等价于假设**人口在 0.1° 块内均匀分布**。块内不均匀时两值不同。单格暴力验算（`m1h`）：目标格 x 100.05–100.15、y 14.75–14.85 的真值 **29,457.0**，管线给 **24,456.5**，差 **−17.0%**；该格恰好整覆盖 12×12 个原始格、在四个 0.1° 块中各占 1/4，而四个块的合计并不等于各块四分之一的合计。

**判定**：

- 模板**落在** LandScan 的聚合块网格上（本仓库真实数据：偏移 3.05e-6°，约 3e-5 格）时，人口场与真值一致到 0.0000%（实测）。
- 模板**不在**块网格上时（区域裁剪、产品原点不同、用户自定 `target_res`），人口在 0.1° 块内被抹平，逐格误差中位 16.6%、最大 119%（实测，V1）。**这是真实数值影响，不是舍入**。
- 是否算缺陷取决于口径：现状是「先聚合到块（守恒）再按块摊（块内均匀假设）」。**建议**：模板不在 pop 聚合块网格上时 `cli::cli_warn()`，把静默的块内抹平变成可见；是否改用真正的细格面积加权（不再先聚合）属于口径变更，需用户拍板。Lead 已将此项列入用户队列，本次不改。

**Q1 的量化补充（Lead 实测，`check-template-reconcile.R`）**：偏移**不需要**大到半格才会出问题。同一幅裁剪后的原分辨率 LandScan、同一个 extent，只换模板的来源：

| 模板 | dim | xmin | res | `.aggregate_pop()` 总量 | 相对精确参照 90,758,858 |
|---|---|---|---|---|---|
| 真实 netCDF 裁出来的（`mortality()` 实际用的） | 87 × 77 | 99.9999983041 | 0.0999999983 | **90,758,837** | **−21（2.3e-7）** |

格心相对人口**聚合格原点**（agg xmin 99.9999999888）的偏移：真实模板 dx = −1.68e-6、dy = −2.07e-6 度；合成模板 dx = +1.1e-8、dy = −3.0e-9 度——差三个数量级。Lead 另测：偏移 **1e-4 度**（约 11 米）约吃 **3,236 人（0.0036%）**。

**含义**：随包的真实文件自身就带 **1.7e-6 度（约 0.19 米）** 的偏移，已足以触发一个**虽小但非零**的损失；`terra::resample(method = "sum")` 只在模板格网与人口聚合格网**重合**时才是严格守恒的聚合，否则每一次运行都在边界块上做一次静默的近似。这正是 Q1 那条护栏（偏移超过阈值就告警）的现实依据，而不是一个理论顾虑。

## 8. `R/AGENTS.md` 第七节第 1 条（分块流式网格引擎）的验收锚点

### 8.1 锚点原文与现状

> **验收锚点**：在随包示例数据上，网格引擎与 `mortality()` 的结果必须逐列一致（复用 `test-fingerprints.R` 的比对方式）。

现状：**网格引擎不存在**（无 `R/grid-engine.R`、`R/tiles.R`）；但锚点的**比对装置已经就绪且已在用**：

- `test-fingerprints.R` 的逐列求和指纹（13 条分支，`ATTRMORT_FINGERPRINTS=1` 触发，参照在 `tests/testthat/fixtures/fingerprints/`）；
- 年龄分块（现引擎的**部分**流式化）已用同样的「逐列一致」方式钉住：`test-grid-path.R` 的 `chunk_ages = 1/3/4/size` 与不分块 `expect_equal(..., tolerance = 1e-12)`，T4 在真实 Lao 数据上复现（`all.equal` TRUE，§4.2）。
- 因此锚点**现在就可复现**，只要新引擎走同一套指纹接口；缺的是引擎本体与「tile 参数 × 分块结果一致性」这层新测试。

### 8.2 本次实测暴露的、必须先解决的问题（不实现引擎）

1. **输入侧的有效格数必须先说清楚**：全球 0.1° 的 netCDF 有 62.9% 是未声明填值 -999（§3）。引擎按「格数」做内存预算前，必须先确定有效掩膜；否则预算按 4.68e6 格算、实际算 1.74e6 格（或反之把填值当数据算进去）。
2. **预算模型要重新标定**：`.chunk_peak_bytes()` 用 `8 bytes × 8 copies`，与实测每行 72.2–92.3 B（10 列长表）差 **2.6–2.9 倍**（§5.4）；引擎的两遍扫描若沿用这个常数，会把「2 GiB 预算」当成 5–6 GiB 用。
3. **「域 ID 栅格」必须先有**：现状 `.attach_admin()` 走矢量栅格化 + 字符键 join（4.68e6 格 × 标签），Lao-only 实测 1.77 s、122.5 MB 对象；引擎计划里的「预生成域 ID 栅格 + 整数索引」是必要前提，否则每遍都要重建字符键。
4. **无标签格的剔除时机**：现状把全世界搬进 join 再 `drop_na()`（806× 浪费，§6.2）。引擎若按「域 ID 栅格有值」扫描，天然只算有标签格——这会让**结果行数与现引擎不同**（现引擎结果里不含无标签格，倒是一致），但会让「N 格进入计算」的统计口径变化，验收锚点要同时钉住**行数与列和**。
5. **分块 × 不确定性的扫描遍数**：现状 `uncertain` 会把整个内核按 CI 链重跑（2–3 条链），每链各自分块；引擎计划「MEAN/LOW/UP 同一块上三联求值」，验收要新增「遍数不随链数增长」的断言（现状无法断言遍数，因为没有可观测的遍数计数器）。
6. **磁盘 I/O 的窗口读写没有先例**：现状全部输入一次读成 data.frame（`raster_to_grid()` 的 `as.data.frame()` 路径，4.68e6 格实测 1.41 s / 40 MB 对象）。`terra::readValues(win=)`/`writeValues()` 在本包的代码里**一次都没用过**，属于全新路径，需要独立的 I/O 正确性测试（对齐、掩膜、非方形分辨率的窗口边界）。

## 9. 落地改动（Lead 批准，独立 commit）

### 9.1 `.aggregate_pop()`：同支撑集的守恒校验（bug 修复，语义不变）

- 基准改为「**输出同支撑集**上的源合计」：先按 §9.2 取窗口，再对窗口求 `terra::global(..., "sum")`；窗口取不到（模板超出源）时**不做总量比较**（两个不同支撑集不可比），并在注释里写明原因与旧数字。
- 守恒语义一字未动（仍是 `|after - before| / |before| > tol` 告警）。

### 9.2 `.aggregate_pop()`：前置裁剪到模板足印

- 新增私有 helper `.pop_window(r, template, step)`：把模板**向外**取整到 `step`（聚合时 = `res_r × round(fact)`，其余 = `res_r`）的整块边界；模板超出源时返回 `NULL`（退回整幅读取）。`.pop_crop()` 把它落成栅格。
- 裁剪点在**源栅格**上（不是聚合结果）：Lao 窗口实读 **964,656** 格而不是 9.33e8 格。
- 「向外」是必须的：`terra::resample()` 会读取每个与目标格重叠的源格，向内取整会改变边缘值；多读一块只花时间、不改数。
- 三个分支（aggregate / disagg / plain）都改成在裁剪后的源上做，`fact` 判定与告警文案未动。
- **修后实测**（`m6-after-fix.R`）：Lao 窗口 **16.14 s → 0.16 s**（**101×**），无告警，输出合计 90,758,858 = 源在同窗口的合计；全局模板下裁剪是空操作，`.aggregate_pop` 由 22.15 s 变 36.4 s——多出的 14 s 是守恒校验现在真的去读一遍源（旧实现是虚报后照跑），属于把校验做实的代价，已在 §10 记为 Info。

### 9.3 新增测试 `tests/testthat/test-validate-pop-conservation.R`

36 项，钉住：窗口整块对齐且覆盖模板；整倍/更细/非整倍/多带四种分支下「读少不改数」；**`res()` 非精确表示时聚合块不移动**（会抓住 §9.5 第 1 条的回归）；窗口外的模板不裁剪也不比总量；**区域输出不再虚报损失**（回归）；告警里的两个数是**足印对**而不是源全局合计或读窗口合计；CRS84 ↔ EPSG:4326 不再触发 `Reprojecting`，真正不同的 CRS 仍然触发。

### 9.5 落地时踩到并修掉的坑（值得留档）

1. **度数算窗口会多 snap 一整格**。`res()` 不是精确值（LandScan 报 `0.0083333333329999992`），用度数算出来的「整块边界」落在真边界下方十亿分之一度，`terra::crop(snap = "out")` 于是向外多取一整格，**把所有聚合块整体挪动**。实测：Lao 窗口 6699 格里 **88 格**与不裁剪路径不同（最大差 0.03125）。修法：窗口先按千分之一格内缩再 snap，并对结果做覆盖率校验（取不到就退回整幅）。新增测试 `res() 非精确表示时聚合块不移动` 专门抓这个回归。
2. **多带源的合计是逐层一个数**。旧代码 `terra::global(...)[[1]]` 在 2 带源上让 `is.finite(total_before) && ...` 直接以 `'length = 2' in coercion to 'logical(1)'` 中止——多带 pop 栅格本来就跑不到底。修法：逐层比较、报「动得最多的那一层」。
3. **比较基准必须是「输出足印」而不是「读窗口」**。裁剪窗口为了对齐块，可能比模板大一整块；拿窗口合计去比模板输出，等于把旧 bug 缩小一号重演。修法：另算模板足印（`.pop_footprint()`），足印隔离不出来时**不比较**。
4. **残余差异（Info，已量化）**：修复后，聚合步与不裁剪路径**逐格完全相同（0/6864 差异）**；重采样步仍有 **88/6699 格**差在最后几位（最大相对 **6.3e-5**，总量逐位相同 90,758,858），来源是 terra 对裁剪后 `res()`（0.099999999995999969 vs 0.099999999995999997）的浮点几何，属边界格纳入/排除的翻转，不是聚合块错位。
